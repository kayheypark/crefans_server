# 베타 실결제·수동 지급 개시 준비 (2026-10-31)

상태: **준비 중**. 코드 스위치와 콘솔 기능은 로컬 구현·검증까지 완료했고, 운영 배포 전이다. 문구 개정안은 아래 초안이며 아직 적용하지 않았다. 시행일은 토스페이먼츠 운영 승인과 통신판매업 신고번호 확인 후 정한다.

## 1. 사용자 결정 (2026-10-31, /ask-me)

| 항목 | 결정 |
| --- | --- |
| 토스 상품 | 일반결제(콩 충전)·자동결제(빌링·구독)·지급대행 모두 신청, 심사 중 |
| 송금 | 운영자가 은행에서 직접 이체하고 콘솔에 기록(지급대행 연동 전) |
| 통신판매업 | 토스 등록 과정에서 신고. 번호 확인 전에는 실결제를 시작하지 않음 |

| 세금 | (2026-10-31 정정·확정) 법령상 회사에 원천징수 의무가 있으면 그 세액은 회사가 수수료 20% 안에서 부담해 신고·납부하고 크리에이터에게는 공제 없이 지급. 크리에이터의 소득세 신고·납부와 사업자 크리에이터의 세무 증빙은 크리에이터 몫. 계약서 별지 A v2.35 반영 |

## 2. 코드 스위치

| 환경값 | 동작 | 기본 |
| --- | --- | --- |
| `LIVE_PAYMENTS_ENABLED=true` | 베타에서도 토스 운영 키(`live_ck_`/`live_sk_`)만 허용. 테스트 키나 섞인 키는 `LIVE_KEYS_REQUIRED`로 거부 | 꺼짐(베타는 테스트 키만) |
| `MANUAL_PAYOUTS_ENABLED=true` | 은행 API 호출 없이 출금을 "이체 대기"로 두고, 운영자가 이체 결과와 계좌 확인을 콘솔에 기록 | 꺼짐 |

- 코드: `src/platform/beta-policy.ts`(스위치·키 검사), `bank-provider.ts`(수동 모드에서 계좌 확인은 `MANUAL_ACCOUNT_REVIEW` 안내, 이체는 대기 반환), `finance.service.ts`·`beans.service.ts`(`manualResult`, `manualVerifyAccount`), `admin.controller.ts`·`beans.controller.ts`(콘솔 API), `jobs.service.ts`(수요일 자동 처리 중 전환).
- 지급은 기존 검사를 그대로 거친다: 수요일, 출금 가능 잔액, 확인된 계좌, 콩은 실제 입금이 확인된 일반콩 출처. 이체 결과는 건당 한 번만 기록되고 감사 로그(`withdrawal.manual_result`, `bean.payout_manual_result`, `account.manual_verified`)에 처리자·참조번호·시각이 남는다.
- 콘솔: 매출·정산 화면의 "수동 지급"(확인 대기 계좌, 이체할 멤버십 출금, 이체 완료 기록·반려), 콩 화면의 "이체 완료 기록". 권한은 매출 `revenue.create`, 콩 `beans.update`.
- 운영 키 입력: 토스 운영 시크릿 키는 사용자가 서버 환경설정에 직접 넣는다(작업 수행자는 운영 키를 입력하지 않는다).

## 3. 운영 절차 (개시 후)

1. 크리에이터가 정산 계좌를 등록하면 콘솔 "확인 대기 정산 계좌"에 나타난다. 통장 사본 등으로 예금주를 확인한 뒤 "예금주 확인 완료"를 누르고 확인 내용을 적는다.
2. 수요일에 신규 출금이 "이체 대기"로 바뀐다(작업자 또는 콩 화면의 "지급 처리").
3. 은행에서 직접 이체한 뒤 "이체 완료 기록"에 이체 참조번호와 시각을 입력한다. 이체하지 못하면 사유를 적어 "반려"한다(멤버십 반려는 출금 가능 잔액으로 돌아감).
4. 기록 전에는 크리에이터 화면에서 "처리 중"으로 보인다. 기록은 되돌릴 수 없으므로 실제 이체 확인 후 기록한다.

## 5. 남은 결정·위험

- **공지 기간**: 약관 제10조는 중요한 변경을 적용 전에 안내하도록 한다. 실결제는 새 결제 동의로만 시작해 기존 계약을 불리하게 바꾸지 않지만, 공지일과 시행일 간격은 사업자 결정이며 법적 최소 기간은 별도 확인이 필요하다.
- **원천징수**: 원천징수 대상 사업소득(인적용역) 지급자는 3%(지방소득세 포함 3.3%) 원천징수와 지급명세서 의무가 있다(소득세법 제127조·제129조, 2차 자료 확인 2026-10-31: https://taxly.kr/post/326, https://www.watax.kr/employment/business-income-withholding). 크레팬스는 멤버십 판매자가 크리에이터이고 회사는 중개자라 멤버십 정산금·콩 후원 수익 지급의 해당 여부는 세무사 확인이 필요하다. "원천징수 없이 지급"은 확정 법적 판단이 아니다.
- **원천징수 조사(2026-10-31 확인, 사용자 질문 '세무를 크리에이터 몫으로 해도 되는가')**: 사례가 갈린다. 팬딩은 스스로 중개자라 밝히면서도 비사업자 크리에이터 정산금에서 3.3% 원천징수, 일반과세자는 역발행 세금계산서 승인 필수(https://docs.channel.io/creator_guide/ko/articles/%EC%A0%95%EC%82%B0-8603c17e , 이용약관 19조 https://docs.channel.io/policy/ko/articles/%EC%84%9C%EB%B9%84%EC%8A%A4-%EC%9D%B4%EC%9A%A9%EC%95%BD%EA%B4%80-a73d365b). 포스타입은 통신판매중개자로서 소득을 직접 지급하지 않는다며 2018년 1월부터 원천징수하지 않고, 출금 수수료에 대한 세금계산서를 발행(https://www.postype.com/en/@blog/post/19252075, 회사가 말한 '국세청 권고' 원문은 미확인). 팬트리는 약관·도움말에 명시 없음(정산 시 주민등록번호 수집은 확인). 법령: 소득세법 제127조①은 원천징수대상 사업소득을 '지급하는 자', 제3호 소득은 사업자 등 대통령령으로 정하는 자로 한정하고 ②는 대리·위임받은 자의 행위를 본인 행위로 봄(법령 미러 casenote, 2차). 국세청 원천징수 안내 https://www.nts.go.kr/nts/cm/cntnts/cntntsView.do?mi=40349&cntntsId=238925 . 부가가치세법 제75조로 통신판매중개자는 판매·결제 명세 제출 의무(원천징수와 별개). 판단(확정 아님): 멤버십은 '크리에이터 판매·회사 중개'가 PG 명의·증빙·계약에서 일관되면 원천징수하지 않는 길이 있으나, 콩 후원 출금은 회사가 콩을 판매하고 현금을 지급하는 구조라 회사가 지급자로 볼 위험이 큼. 계약으로 법정 원천징수 의무를 면제할 수는 없음. 세무사·국세청 서면질의 필요. 원 조사: 프론트 `.local/night-work/2026-10-30-0714.md` 356-365행, `2026-10-30-1414.md` 193-198행.
- **회사 부담 원천징수의 후속 과제(2026-10-31 결정 후)**: ①회사가 세액을 떼지 않고 대신 부담하면 그 부담액도 크리에이터 소득으로 보아 세액을 다시 계산(gross-up)해야 하는지 세무사 확인 필요(확인 전 추정, 근거 미확인). ②원천징수를 한다면 매달 신고·납부, 간이지급명세서·지급명세서 제출과 크리에이터 주민등록번호 수집이 필요하며 개인정보 처리방침·출금 화면 수집 항목 개정이 따름. ③의무 여부 자체(콩 출금·멤버십 각각)는 국세청 서면질의나 세무사로 확정.
- **토스 승인 범위**: 자동결제(빌링)는 별도 심사 대상이다. 승인된 상품만 실결제를 연다(예: 빌링 미승인 시 구독 실결제 보류).
- **웹훅·결제창 설정**: 토스 개발자센터의 운영 웹훅 URL 등록과 운영 키 교체 후 소액 실결제·취소 1회로 확인한다(실제 청구, 사용자 승인 필요).
- **세무 문구**: 약관·계약서의 "세금 처리 방식은 정식 정산 전 안내"는 결정에 맞게 별도 개정 필요.
