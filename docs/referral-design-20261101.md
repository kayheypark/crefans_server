# 레퍼럴(친구 초대) 보상 설계 — 2026-11-01

상태: 설계·구현 중. 기능 스위치 `REFERRAL_ENABLED`(기본 off)로 배포하며 켜는 시점은 사업자 결정.

## 사용자 결정(2026-10-31~11-01, 클릭형 질문 답변)

| 항목 | 결정 |
| --- | --- |
| 대상 | 팬·크리에이터 모든 회원. 레퍼럴 테이블 고유 ID 행을 회원 고유 ID와 조인 |
| 받는 사람 | **직접 초대한 회원만**(1단계). 추천인의 추천인에게는 주지 않음 |
| 지급 조건 | 초대받은 회원의 **첫 유료 결제 1회**(멤버십 또는 콩 충전), 결제 즉시 지급 |
| 회수 | 그 결제가 환불되면 보상 회수. 이미 출금했다면 콩 미수금으로 남김 |
| 보상 | **출금 가능 프로모션 콩 100개**(1콩 기준가치 100원) |
| 출금 조건 | 후원 수익과 같음: 최소 1,000콩, 수수료 20%, 본인 명의 확인 계좌, 화요일 23:59 마감·수요일 지급. 팬도 출금 가능해야 함 |
| 가입 | 레퍼럴 링크로 들어오면 운영자 초대 없이도 가입 허용(스위치 on일 때) |

## 기존 프로모션 콩과의 차이

- 기존 프로모션콩(`bucket=promotion`): 받은 사람은 출금 불가, 후원에만 사용. 후원받은 크리에이터의 `earned-promotion` 로트가 되어야 출금 가능(출처 검사: 지급→후원 할당 대조).
- 레퍼럴 보상콩: 받은 사람의 `earned-promotion` 로트로 바로 적립하고, 출처는 `referral_signups` 행으로 검사한다. 출금 경로·수수료·최소 수량은 기존 후원콩과 공유한다.

## 구현(서버)

- 테이블: `referrals`(회원당 1행, id=초대 코드), `referral_signups`(초대받은 회원 1행, 보상 상태). 마이그레이션 `20261101090000_referrals`.
- 가입: `POST auth/signup/email/request`·`auth/signup`에 `referralCode`. 스위치 on + 유효 코드면 운영자 초대 없이 통과하고 가입 트랜잭션에서 관계를 기록. 스위치 off거나 코드가 없으면 기존 초대 규칙 그대로.
- 지급: 멤버십 `finalize`, 콩 충전 승인(`applyProvider` DONE) 트랜잭션 안에서 `grantReferralReward`. **실결제(live)만** 인정(테스트 키 결제로 출금 가능 콩이 생기지 않게). 초대받은 회원당 1회.
- 원장: 회사 재고(stock) → 추천인 `earned-promotion` 100콩, 로트 `grant_id=referral_signups.id`, 보류 없음. 출금 출처 검사(`fundedLots`)가 이 행을 근거로 인정.
- 회수: 멤버십 `completeRefund`, 콩 `finishRefund`(부분 환불 포함)·`freezeCharge`(분쟁)에서 `clawBackReferralReward`. 남은 콩은 재고로 되돌리고 로트를 동결. 이미 출금된 몫은 `creator_receivables`(kind beans, 순액)로 남겨 이후 콩 출금을 막음.
- 출금: 보상을 받은 회원은 크리에이터가 아니어도 콩 출금 화면·정산 계좌 등록·출금 PIN 설정을 쓸 수 있음(`requireBeanPayoutMember`). 멤버십 수익 출금은 크리에이터 전용 유지.
- 조회: `GET me/referral` — 코드와 집계(초대 수, 보상 건수·콩)만. 초대받은 회원의 개인정보·결제 정보는 돌려주지 않음.
- 검증: `tests/platform-referrals.test.cjs` 6건(대조: 출처 검사 제거 시 1건, live 조건 제거 시 3건 실패), 기존 회귀 104건 통과.
- 알려진 한계: 결제 트랜잭션에서 결제자 지갑 다음에 추천인 지갑을 잠가 잠금 순서가 고정 정렬과 다를 수 있음(교착 가능성 낮음, 재시도 대상).
